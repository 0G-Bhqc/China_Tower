# 中国楼阁 3D 资产分析与 Three.js 落地方案 V2

更新日期：2026-08-13  
适用范围：岳阳楼、黄鹤楼、滕王阁、飞云楼、蓬莱阁 5 个 `.max` 参考资产，以及无 3D 源资产的鹳雀楼。

## 1. 决策摘要

工程分成两条严格隔离的轨道：

- **证据轨**：不可信 `.max` -> 隔离净化 -> FBX -> Blender 后台分析 -> MCP 抽查 -> 可追溯 JSON/多通道渲染。
- **产品轨**：结构化证据 -> `PavilionSpec` -> 共享古建构件库 -> 程序化 Three.js -> 多角度门禁 -> 单 HTML 打包。

两轨之间只能传递 JSON、测量值、审查图和经批准的独立材质证据。源网格、源脚本、源 GLB/FBX 不进入产品运行时，也不复制拓扑成为最终程序化模型。

相比第一版方案，V2 的主要优化是：

1. MCP 从“重型执行器”调整为“编排和审计入口”；批量工作由版本固定的 Blender 后台脚本完成。
2. 每个资产先导出轻量分析代理，再按需处理全量场景，避免 5 个大场景阻塞同一流水线。
3. 不为每座楼、每个阶段生成一份完整 Three.js 工厂；先建设共享 primitives/runtime，再用小型规格驱动一个装配器。
4. 岳阳楼不重做：将 Blender 测量作为当前 `form-refinement` 的校准证据，只生成差异报告和有阈值的修正。
5. 把安全、语义置信度、测量、视觉、结构、性能和打包拆成独立硬门禁，任何全局分数都不能覆盖关键构件失败。

## 2. 目标架构

```text
不可信源资产
  .max + textures
      |
      v
[G0 隔离与安全]
  hash + 脚本禁用 + 净化副本
      |
      v
[G1 3ds Max 转换]
  analysis-proxy.fbx + full-scene.fbx + conversion-report.json
      |
      v
[G2 Blender 确定性分析]
  inventory / hierarchy / clusters / measurements / six-pass renders
      |
      +---- MCP：启动任务、读取状态、复核异常、批准语义标签
      |
      v
[G3 证据归一化]
  source-evidence.json + confidence + Three.js 坐标变换
      |
      v
[G4 PavilionSpec]
  只保留尺寸、比例、曲线、重复规律、材料族和不确定性
      |
      v
[G5-G8 程序化构建与审查]
  shared primitives -> pavilion assembler -> multi-angle/runtime/perf gates
      |
      v
[G9 自包含交付]
  single HTML / zero runtime requests
```

## 3. 工程目录建议

开发期保持模块化，发布期再内联成单文件：

```text
src/
  app/                    # 场景、UI、时间线、楼阁切换
  core/                   # renderer、资源释放、质量档位、运行时类型
  primitives/             # sweep/ring/tube/lathe/roof/tile/dougong 等
  materials/              # 独立 PBR 通道、程序纹理、调色板
  pavilions/
    specs/                # 每座楼的小型 PavilionSpec
    assemblePavilion.ts   # 一个共享装配入口
  review/                 # semantic/silhouette/depth/normal/material 通道
pipeline/
  max-conversion/         # 隔离机脚本与导出预设，不在网页构建中执行
  blender/                # 后台分析脚本和 MCP 适配层
schemas/                  # 证据、分析、PavilionSpec、审查合同
evidence/pavilions/<id>/  # 不进入生产 bundle 的证据
dist/                     # 最终网页
```

当前三个岳阳楼工厂文件先冻结。共享库通过“迁移一个可复用系统、验证等价、再迁移下一个”的绞杀式方式建立，禁止一次性重写现有成果。

## 4. 三种数据合同

### 4.1 SourceAssetManifest

只描述来源与安全状态：源文件哈希、Max/V-Ray 版本、贴图列表、脚本检测、隔离环境、净化副本和转换日志。它不包含任何建筑语义判断。

### 4.2 BlenderAnalysis

只描述观察和计算结果：

- 原始坐标系、单位、归一化矩阵和包围盒；
- 对象、网格、材质、实例、顶点、三角面和异常统计；
- 原始层级与基于空间/重复/材质的聚类假设；
- 标准相机及 beauty、silhouette、semantic ID、depth、normal、material ID 六通道；
- 总体和分层测量，每项包含 `value`、`unit`、`source`、`confidence`；
- 丢失插件、贴图、材质降级、断裂层级和未解决问题。

聚类只能叫 `hypothesis`，除非对象名、空间结构、重复规律和人工复核中至少两个证据源一致。

### 4.3 PavilionSpec

只描述产品端如何独立重建：楼层、平面、柱网、梁枋、斗拱、栏杆、门窗、屋面、瓦作、脊兽/宝顶、重复系统、材料族、建造阶段、点击/爆炸分组和预算。每个关键参数携带证据引用和置信度。

不得把 Blender 对象 ID、FBX 网格路径或原资产拓扑作为构建依赖。

## 5. 优化后的转换策略

### 5.1 G0：隔离与安全

五个场景均检测到脚本化自定义属性。转换必须在离线虚拟机或一次性转换机完成：

- 原文件只读挂载，先生成 SHA-256 清单；
- 禁用启动脚本、场景脚本、自定义属性脚本和系统命令；
- 不执行未知插件安装，不运行场景提示的任何脚本；
- 净化后另存新文件，原件不覆盖；
- 转换机产出物经过恶意内容扫描后，才可进入 Blender 分析机。

若无法证明脚本执行被禁用，G0 失败，流水线必须停止。

### 5.2 G1：双层导出

每个场景生成两种 FBX：

- `analysis-proxy.fbx`：保留层级、名称、实例和包围盒；网格按对象降至可交互级别，材质只保留槽位与基础颜色。用于快速盘点、语义标注和相机设置。
- `full-scene.fbx`：保留原几何与 UV，按资产分批导出；只在代理分析通过后用于精确测量和局部审查。

两种文件都使用米制、显式轴变换、三角化结果可复现，并输出同一份对象映射表。V-Ray 材质无法稳定转换时，允许几何优先降级，不阻塞结构分析。

### 5.3 资产分片策略

- 岳阳楼：整场代理 + 整场全量，作为 PoC。
- 黄鹤楼：按楼层和屋顶分片，优先分析方转八边及五层轮廓。
- 滕王阁：按高台、主体、屋面分片；检查少对象/高面数的合并网格。
- 飞云楼：按连通分量和空间八分区分片；先做代理，不承诺恢复源语义。
- 蓬莱阁：先按空间建筑群分区，再按对象重复变换聚类；禁止一次导入 9,065 对象后人工逐个整理。

## 6. Blender 与 MCP 的职责边界

### Blender 后台脚本负责

- 导入、单位/轴检测、包围盒和异常统计；
- 实例/重复变换发现、连通分量和空间聚类；
- 固定相机和六通道批量渲染；
- 测量与证据 JSON 导出；
- 任务恢复、内容哈希、确定性随机种子和日志。

### MCP 负责

- 创建或恢复一次分析任务；
- 查询任务状态和产物；
- 对异常对象、低置信度聚类和关键尺寸进行交互复核；
- 批准/拒绝语义标签；
- 请求局部重跑或额外视图。

### MCP 不负责

- 逐对象执行上万次同步调用；
- 在会话里临时改模型后把它视为产品实现；
- 直接把 Blender 网格导出为最终 Three.js 资产；
- 在缺失语义 ID 时用整体色彩或轮廓分数冒充构件级证据。

建议 MCP 暴露最小工具集：`start_analysis`、`get_status`、`list_issues`、`inspect_cluster`、`approve_label`、`render_extra_view`、`export_evidence_bundle`。所有工具均以 `jobId` 幂等执行。

## 7. Three.js 架构优化

### 7.1 先消除扩展性瓶颈

当前岳阳楼 blockout、structural、form 三个工厂分别约 130 KB、241 KB、248 KB。按“楼阁 × 阶段”复制会造成代码、材质、运行时和 primitive 大量重复。在第二座楼开始编码前，必须完成：

1. 提取公共 `ProceduralModelOptions`、runtime、相机、灯光和材质创建器。
2. 提取矩形柱网、环廊栏杆、斗拱重复、屋面曲线和瓦片实例化系统。
3. 用 `detailLevel: blockout | structural | form | material | final` 控制单一装配器，不再为每阶段生成完整副本。
4. 所有重复构件优先 `InstancedMesh`；只有影响主轮廓、需要独立拾取或独立动画的构件保留独立 Mesh。
5. 生产代码不得内嵌完整分析 JSON，只保留经过筛选的 `PavilionSpec`。

### 7.2 共享古建 primitive 路线

按复用收益排序建设：

1. 基础与台基：矩形/多边形台座、踏步、线脚。
2. 柱网与梁架：矩形、方转八边、回廊、楼层收分。
3. 栏杆与门窗：节距驱动的实例系统。
4. 斗拱：如意、简化宋式、密集元明式三个参数族。
5. 屋顶：歇山、攒尖、盔顶、十字歇山四个连续曲面策略。
6. 瓦作：筒瓦/板瓦/滴水/瓦当的分层实例化和移动端降级。
7. 脊饰与宝顶：曲线管、车削和少量独立英雄构件。

屋顶连续曲面与屋檐轮廓不能用一组互不相接的盒子代替；斗拱和瓦片则应以少数标准单元实例化。

### 7.3 Three.js 版本

工程文档提到 r149，当前项目实际锁定 `three 0.179.1`。V2 以本地锁文件和类型检查为执行真值，冻结 0.179.1 直至六楼阁核心构件库稳定；不要在资产迁移同时升级引擎。发布文档应同步修正版本描述，避免双重真值。

## 8. 质量与性能门禁

| 门禁 | 通过条件 | 失败动作 |
| --- | --- | --- |
| G0 安全 | 原件哈希、脚本禁用、净化日志齐全 | stop |
| G1 转换 | 代理可读；单位/轴/层级映射明确；异常有报告 | refine-input |
| G2 语义 | 关键构件有证据和置信度；合并网格不冒充精确语义 | request-review |
| G3 测量 | 总体尺寸、层高、檐挑、柱网和屋顶比例完整 | request-input |
| G4 规格 | 所有关键测量映射到组件或材料字段；隐藏面有假设 | refine-spec |
| G5 轮廓 | 固定视图硬门禁通过；关键特征逐项通过 | refine-code/spec |
| G6 多角度/结构 | 四向与俯视不退化；无浮空构件；部件覆盖通过 | refine-code |
| G7 材质 | PBR 通道独立；中性光和掠射光均可读 | refine-material |
| G8 运行时 | 可点击/爆炸定义一致；实例、释放和切换稳定 | refine-code |
| G9 性能/交付 | 桌面/移动预算及单文件零请求检查通过 | optimize/stop |

性能预算按“同时仅展示一座楼阁”分配：

- 桌面：楼阁软上限 450k 三角形、硬上限 600k；楼阁自身不超过 12 draw calls；全场不超过 1.5M/25。
- 移动：楼阁软上限 220k、硬上限 300k；楼阁自身不超过 8 draw calls；全场不超过 0.8M/20。
- 任何 8k 源图不直接进入产品；材质按视觉收益裁剪、去光照、重建独立通道并压缩。
- 切换楼阁后必须释放上一个楼阁的 geometry、material、texture 和 render target；设自动内存回归测试。

## 9. 岳阳楼增量校准规则

当前状态是 `form-refinement`，不初始化新 reconstruction，也不覆盖现有证据。Blender 结果进入 `evidence/pavilions/yueyang/blender/`，先生成 `calibration-delta.json`：

- 总高/宽/深偏差 <= 2%：保留现有值。
- 楼层高度比例偏差 <= 3%：保留现有值。
- 檐挑、柱网、盔顶母线偏差 <= 5%：保留现有值。
- 超过阈值：只修改对应规格字段，记录旧值、新值、证据、原因和受影响 primitive。

先修相机，再修主轮廓，再修层间比例，再修盔顶/檐口，最后才处理材质与灯光；一次修正只处理一个问题组。

## 10. 实施批次与退出标准

### Batch 0：基础设施

产出：隔离转换 SOP、导出预设、分析合同、任务目录、JSON 校验器。  
退出：`validate:asset-pipeline` 通过；岳阳楼原件哈希和净化报告齐全。

### Batch 1：岳阳楼纵向 PoC

产出：代理/全量 FBX、完整 Blender 证据、校准差异、现有 form 模型的有限修正。  
退出：G0-G8 全链通过，且没有推倒已有程序化工厂。

### Batch 2：共享构件库

产出：公共 runtime/material/primitives、单装配器、多 detail level；岳阳楼视觉和结构回归。  
退出：岳阳楼结果不退化，工厂重复代码显著下降，第二座楼无需复制整份工厂。

### Batch 3：黄鹤楼 + 滕王阁

黄鹤楼验证方转八边、多层收分和攒尖宝顶；滕王阁验证高台、重檐歇山和大体量。  
退出：两座楼均由规格驱动同一装配器，关键识别特征通过逐项门禁。

### Batch 4：飞云楼 + 蓬莱阁

飞云楼验证合并扫描资产的假设分割和密集斗拱实例化；蓬莱阁验证多建筑群装配。  
退出：低置信度区域被明确标注，没有把自动聚类当作建筑史真值。

### Batch 5：鹳雀楼与最终交付

鹳雀楼走照片/文档证据路径，不伪造 3D 源资产；完成六楼切换、切片建造、性能和单文件打包。  
退出：G9 通过，运行时无外部模型请求、无网络依赖。

## 11. 最短下一步

1. 在隔离转换机上只处理岳阳楼，生成原件 SHA-256、净化日志、`analysis-proxy.fbx` 和 `conversion-report.json`。
2. 安装固定版本 Blender，并让后台分析脚本在无 MCP 情况下也能完整运行；MCP 只是调用同一任务入口。
3. 跑出岳阳楼六通道与 `measurements.json`，生成与现有规格的差异报告。
4. 在差异审查通过后，再提取第一个共享 primitive；不要同时启动第二座楼编码。
5. 修复 `forge/next.py` 对 187 KB 规格文件连续超时的问题，或为状态查询增加不解析完整规格的快速模式。
